# Инкремент 14. Аутентификация, удаление URL и Soft Delete

Важный инкремент - аутентификации через подписанные куки. Это стандартная практика в вебе, которая позволяет серверу доверять данным в куке, не храня сессии на своей стороне.

В задании есть подсказка: «симметрично подписанную куку». Это значит, что вы должны использовать HMAC (Hash-based Message Authentication Code) с секретным ключом. В Go для этого есть стандартные пакеты crypto/hmac и crypto/sha256.

Как это работает:
1. Секретный ключ: У сервера есть секретная строка (например, super-secret-key). Она никогда не покидает сервер.
2. Создание куки: Когда пользователь создаёт ссылку, сервер генерирует user_id (UUID) и подписывает его: signature = HMAC_SHA256(user_id, secret).
3. Установка куки: Сервер отправляет куку в формате user_id.signature.
4. Проверка куки: Когда приходит запрос, сервер берёт user_id из куки, снова вычисляет подпись и сравнивает её с той, что в куке. Если подписи совпадают — кука подлинная.


## Что сделано
- **Аутентификация через подписанные куки:**
  - Создан пакет `auth` с функциями `CreateCookie` и `GetUserID`.
  - Кука содержит `user_id` и HMAC-подпись (`sha256` + секретный ключ).
  - При отсутствии или невалидности куки сервер возвращает `401 Unauthorized` (для защищённых эндпоинтов).
- **Эндпоинт `GET /api/user/urls`:**
  - Возвращает только URL текущего пользователя.
  - Если URL нет — `204 No Content`.
- **Эндпоинт `DELETE /api/user/urls`:**
  - Принимает массив `correlation_id` (или коротких кодов).
  - Возвращает `202 Accepted`.
- **Soft Delete (мягкое удаление):**
  - В таблицу `urls` добавлено поле `deleted BOOLEAN DEFAULT FALSE`.
  - При удалении записи не стираются физически, а помечаются как `deleted = TRUE`.
  - Это позволяет серверу «помнить» о существовании URL и возвращать `410 Gone` вместо `404 Not Found`.

## Зачем
- **Аутентификация:** Защищает данные пользователя от несанкционированного доступа.
- **Soft Delete:** Позволяет отличать «URL никогда не существовал» (`404`) от «URL был, но удалён» (`410`). Это стандарт HTTP и требование автотестов.
- **Восстановление данных:** В будущем можно легко «отменить» удаление, просто сбросив флаг.

## Проблемы и решения
- **Проблема:** Автотест `check_state` ожидал `410 Gone`, а сервер возвращал `404 Not Found` для удалённых URL.
- **Причина:** Записи удалялись физически (`DELETE FROM urls`), и сервер не мог отличить удалённый URL от несуществующего.
- **Решение:** Внедрён Soft Delete. Записи помечаются флагом `deleted = TRUE`, а `RedirectHandler` проверяет этот флаг и возвращает `410 Gone`.
- **Проблема:** `CREATE TABLE IF NOT EXISTS` не добавляет новое поле в существующую таблицу. (тут по факту удалил текущую таблицу, и в схему добавил новое поле, после запуска сервера таблица создаться новая с доп. полем. А так в проф. разработке для это применяют "миграции", т.к. каждый раз удалять таблицу нет возможности, просто потеряешь данные)
- **Решение:** В `NewPostgresStorage` добавлен `ALTER TABLE urls ADD COLUMN IF NOT EXISTS deleted BOOLEAN DEFAULT FALSE`. (Это вот так по хорошему нужно решать эту ситуацию, или через миграцию)

## Результат
- Все автотесты для инкремента 14 пройдены.
- Сервер корректно различает `404` (не найдено) и `410` (удалено).
- Логика удаления соответствует стандартам HTTP.


## Важность:
- Готовность к будущему: Soft Delete — это стандартная практика в реальной разработке, а не только «костыль для теста».
