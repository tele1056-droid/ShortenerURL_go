# Инкремент 6. Логирование запросов и ответов через middleware

## Что сделано
- Установлен пакет `go.uber.org/zap`.
- Создан пакет `internal/middleware` с функцией `LoggerMiddleware`.
- `LoggerMiddleware` оборачивает `http.ResponseWriter` в кастомную структуру `responseWriter`, чтобы перехватывать код статуса (`WriteHeader`) и размер ответа (`Write`).
- Middleware логирует URI, метод, время выполнения, код статуса и размер ответа на уровне `Info`.
- В `main.go` создан логгер и подключен через `r.Use(...)` в роутере `chi`.

## Зачем
- **Наблюдаемость:** Логирование запросов и ответов — основа для отладки и мониторинга.
- **Стандартизация:** `zap` — быстрый и структурированный логгер, стандарт де-факто в Go-сообществе.
- **Middleware:** Позволяет вынести сквозную логику (логирование) из хендлеров, соблюдая принцип единственной ответственности.

## Проблемы и решения
- **Проблема:** Стандартный `http.ResponseWriter` не отдает код статуса и размер ответа после записи.
- **Решение:** Создана структура `responseWriter`, которая встраивает `http.ResponseWriter` и перехватывает вызовы `WriteHeader` и `Write`.


## Куда будут писаться логи?
В текущей версии с zap.NewProduction() логи по умолчанию будут писаться в stderr (стандартный потом ошибок). При запуске сервера через go run или из терминала, логи будут прямо в консоли.

В индустрии современный стандарт (особенно для приложений в Docker или Kubernetes) - это писать логи в stdout или stderr, а не в файлы.
Потомучто:
- Сборщики логов: Среда исполнения (Docker, systemd, Kubernetes) сама перехватывает поток вывода и перенаправляет его туда, куда нужно (в файлы, в систему анализа логов вроде ELK или Grafana Loki) 
- Простота: Приложению не нужно думать о ротации файлов, правах доступа и очистке диска.

Если нужно чтобы журналы логов велись в файле, можно перенаправить вывод при запуске в терминале:
go run ./cmd/shortener > app.log 2>&1
После этого все логи (и обычные, и ошибки) попадут в файл app.log

## Другие хорошие сторонние библиотеки
- **zap (используется)** — это очень быстрый и производительный логгер, который отлично документирован. Его API интуитивно понятен, а для новичков у него есть удобный SugaredLogger, который позволяет писать логи в привычном printf-стиле.
- **zerolog** — тоже отличный и очень быстрый выбор, но его API построен на цепочках вызовов (log.Info().Str("key", "value").Msg("message")), что может быть немного необычно поначалу.
- **logrus** — самый простой и понятный, но он находится в режиме поддержки, и сообщество рекомендует использовать zap или zerolog для новых проектов.
