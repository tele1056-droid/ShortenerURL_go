# Инкремент 13. Обработка дубликатов URL (409 Conflict)

## Что сделано
- **Уникальный индекс в PostgreSQL:**
  - В схему таблицы `urls` добавлено ограничение `UNIQUE` на поле `original_url`.
  - Это гарантирует, что в базе не может быть двух записей с одинаковым исходным URL.
- **Обработка ошибки `UniqueViolation`:**
  - В `PostgresStorage.Save` добавлена проверка ошибки PostgreSQL через `pgerrcode.UniqueViolation`.
  - Если конфликт вызван полем `original_url`, возвращается кастомная ошибка `storage.ErrURLExists`.
  - Для `MemoryStorage` и `FileStorage` проверка на дубликат выполняется вручную: перед сохранением перебираются все записи, и если `original_url` уже существует, возвращается `ErrURLExists`.
- **Новый метод `GetByOriginalURL`:**
  - Добавлен в интерфейс `Repository` и реализован во всех хранилищах.
  - Позволяет получить существующий `short_url` по оригинальному URL.
- **Обновление хендлеров:**
  - В `ShortenHandler` и `JSONShortenHandler` добавлена обработка `ErrURLExists`.
  - При конфликте возвращается `409 Conflict` и уже существующий короткий URL в правильном формате (`text/plain` для `ShortenHandler`, `application/json` для `JSONShortenHandler`).

## Зачем
- **Целостность данных:** Уникальный индекс предотвращает появление дубликатов в базе.
- **Идемпотентность:** Повторное сокращение одного и того же URL не создаёт новую запись, а возвращает уже существующую ссылку.
- **Обратная совместимость:** Существующие эндпоинты продолжают работать, но теперь корректно обрабатывают конфликты.

## Проблемы и решения
- **Проблема:** `CREATE TABLE IF NOT EXISTS` не добавляет `UNIQUE` в уже существующую таблицу.
- **Решение:** Таблицу пришлось удалить и создать заново (в учебном проекте это допустимо). В реальной разработке для этого используются миграции (например, `ALTER TABLE`).
- **Проблема:** В `MemoryStorage` и `FileStorage` нет встроенной проверки уникальности.
- **Решение:** Добавлена ручная проверка на дубликат перед сохранением.

# Заметка: Разрывы в последовательности ID (Gap in Sequence) при дубликатах

## Контекст
В проекте `ShortenerURL_go` (инкремент 13) при отправке POST-запросов с дублирующимися URL было замечено, что в таблице `urls` появляются «дырки» в поле `id`.

**Пример:**
1. Отправили `http://i7ffbipcdtdn6.com/p7obi` → запись сохранилась с `id = 1`.
2. Отправили тот же URL ещё два раза → дубликаты не записались, вернулся существующий `short_url = "1"`.
3. Отправили новый URL `http://cxepqyimrf.net/...` → запись сохранилась с `id = 4` (а не `id = 2`).

## Причина
Поле `id` объявлено как `SERIAL` (или `GENERATED ... AS IDENTITY`). PostgreSQL при каждом `INSERT` **сначала выделяет следующий номер из последовательности**, а уже потом проверяет ограничения (например, `UNIQUE` на `original_url`).

Если вставка отклоняется (дубликат), **выделенный номер «сгорает»** и не возвращается обратно. Это сделано для производительности и безопасности при параллельных запросах.

## Это нормально?
**Да.** Разрывы в последовательности — это ожидаемое поведение реляционных СУБД. `id` гарантирует уникальность, но не непрерывность.

## Что делать
1. **Ничего не делать** — если автотесты проходят и логика работает, это не является багом.
2. Если нужен «непрерывный порядок» для отображения (например, пользователю), использовать отдельное поле, например `created_at` (время создания), а не `id`.
3. **Не пытаться «исправить»** последовательность запросами вроде `ALTER SEQUENCE ... RESTART` — это сломает данные и вызовет конфликты.

## Вывод
«Дырки» в `id` — это не ошибка, а особенность работы PostgreSQL. Главное — уникальность и корректная логика обработки дубликатов, которые в проекте работают правильно.
