# Инкремент 11. Подключение PostgreSQL и автосоздание таблиц. PostgreSQL как основное хранилище

## Что нужно и не нужно делать в инкременте:
В pgAdmin самостоятельно создавать таблицы не нужно. По условию задания: "Сервису нужно самостоятельно создать все необходимые таблицы", это значит, что таблицы должны созаваться автоматически в коде при запуске сервера. В pgAdmin только самостоятельно создается пустая база данных, а таблицы внутри этой базы создает код.

## Для чего это нужно?
1. Автотесты на GitHub: Когда код запустится на серверах GitHub, там не будет никакого pgAdmin, и никак не получится вручную (самостоятельно) создать таблицу. Код должен это сделать сам.
2. Чистота: Такой подход позволяет развернуть проект где угодно (на другом компьютере, в Docker) - вы просто даете строку подключения, и сервер сам подготавливает структуру.

Для этого используем `CREATE TABLE IF NOT EXISTS`, этот SQL запрос:
- Если таблицы нет - она создастся.
- Если таблица уже есть - ничего не произойдет (таблицане будет вновь создаваться, ошибки не будет)
Благодаря этому можно запускать сервер сколько угодно раз, и он не будет падать с ошибкой "таблица уже существует".

Так сказать задание требует каскадного отказоустойчивого выбора: если DATABASE_DSN задан — используем БД, иначе файл, иначе память.

# Инкремент фактически выполнен:
- Сервер подключается к PostgreSQL.
- Данные сохраняются в БД (тест inspect прошел).
- Сервер корректно завершается по сигналу (проверялось вручную).
- Ошибка возникает только из-за особенности Windows, а не из-за логики.

## Как "пройти" автотест:
1. Запустить автотест в WSL (Windows Subsystem for Linux).
В WSL сигналы работают как в Linux, и код выхода будет 0. Установите WSL (если не установлен), скопируйте проект и запустите автотест там.
2. Запустить автотест в Docker-контейнере с Linux.
Можно запустить контейнер с образом golang и прогнать тесты внутри него.

## Что сделано
- Создана реализация `PostgresStorage` в пакете `storage` (файл `postgres.go`), которая реализует интерфейс `Repository`.
- В `NewPostgresStorage` автоматически создается таблица `urls` (через `CREATE TABLE IF NOT EXISTS`), если её нет.
- В `main.go` реализован каскадный выбор хранилища:
  1. Если задан `DatabaseDSN` (`-d` или `DATABASE_DSN`) — используется **PostgreSQL**.
  2. Если БД не задана, но есть `FileStoragePath` (`-f` или `FILE_STORAGE_PATH`) — используется **файл**.
  3. Иначе — **память**.
- Добавлена корректная обработка сигналов `SIGINT` и `SIGTERM` для **graceful shutdown**:
  - Сервер запускается в горутине, а `run()` ожидает сигнал.
  - По сигналу вызывается `server.Shutdown()`, что позволяет корректно закрыть соединения с БД и завершить процесс с кодом `0`.
- В `main()` убран `panic(err)` — заменен на `os.Exit(1)` с логированием, чтобы избежать неконтролируемого падения.

## Зачем
- **Персистентность:** PostgreSQL обеспечивает надежное хранение данных в промышленных масштабах.
- **Гибкость конфигурации:** Сервис может работать как с БД, так и без неё (для тестов или локальной разработки).
- **Graceful shutdown:** Корректное завершение важно для предотвращения потери данных и корректной работы в контейнерах (Docker, Kubernetes).

## Проблемы и решения
- **Проблема:** Автотест `check_after_restart` падал с ошибкой «Процесс завершился с не нулевым статусом 1».
- **Причина:** На Windows обработка сигнала `SIGINT` приводит к коду выхода `1`, даже если сервер корректно завершается. Это особенность ОС, а не ошибка в коде.
- **Решение:** В реальной разработке тесты запускаются в Linux (GitHub Actions, WSL, Docker), где этой проблемы нет. Код `main.go` корректно обрабатывает сигналы (подтверждено ручным запуском: в логе появляется «Завершение работы сервера...»).

## Результат
- Логика с PostgreSQL полностью реализована.
- Подтесты `shorten` и `inspect` пройдены успешно (данные сохраняются в БД).
- Ошибка `check_after_restart` вызвана ограничениями Windows и не влияет на работоспособность сервиса.

# Странные записи ("Призраки в базе данных") в базе при использовании автотестов
## 📌 Ситуация
Вы запускаете сервер, делаете два POST-запроса через `curl`, открываете pgAdmin, а там:
*   В `original_url` первой записи лежит странная ссылка вида `http://ubry1posvsjof.ru/...`
*   Ваша первая ссылка (`https://123-unique-test-site.com/...`) вообще не первая, а вторая (или её нет).

## 🔍 Почему так происходит
**Автотесты — это «невидимые» клиенты вашего сервера.** 
Когда вы запускаете `shortenertest.exe`, он сам запускает ваш сервер, стучится в него и **пишет данные в базу**. 

Если вы запускали автотесты (например, 10-й или 11-й инкремент) до того, как начали делать свои `curl`-запросы, автотест уже успел:
1. Сгенерировать случайную ссылку через `generateTestURL()` (вот эти `.ru` и `.net`).
2. Отправить POST-запрос на ваш сервер.
3. Сохранить результат в базу.

## 🧩 Что происходит по шагам (хронология)
1. Вы запускаете сервер.
2. Вы (или система) запускаете автотест. 
3. Автотест делает POST-запрос с ссылкой `http://ubry1posvsjof.ru/...`.
4. Ваш сервер сохраняет её как `uuid="1"`.
5. Вы делаете свой первый ручной запрос с `https://123-unique...`.
6. Ваш сервер видит, что `1` уже занят, и выдает `uuid="2"`.
7. Вы делаете второй ручной запрос с `https://1234-unique...`.
8. Сервер выдает `uuid="3"` (но в pgAdmin вы можете её не видеть, пока не нажмёте «Обновить»).

## 🛠️ Как проверить, что сервер работает правильно (чистый тест)
Чтобы убедиться, что ваш сервер не «придумывает» ссылки, а пишет именно то, что вы ему дали:

1. Остановите сервер (`Ctrl + C`).
2. В pgAdmin выполните запрос: 
   ```sql
   TRUNCATE TABLE urls;
   (Или DELETE FROM urls; — это очистит таблицу)
3. Запустите сервер заново.
4. Сделайте только один свой curl-запрос.
5. Обновите результаты записей (f5)
Важно: Автотесты и ручные curl-запросы пишут в одну и ту же базу. Если вы хотите вести «чистые» эксперименты, всегда очищайте таблицу перед ручной проверкой (или используйте отдельную базу для тестов).
