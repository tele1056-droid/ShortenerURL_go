# Инкремент 4. Добавление возможности конфигурирования сервиса при помощи аргументов командной строки

## Что сделано
- Создан новый пакет `internal/config`.
- В пакете `config` описана структура `Config` с полями:
  - `ServerAddress` — адрес запуска HTTP-сервера (флаг `-a`).
  - `BaseURL` — базовый адрес результирующего URL (флаг `-b`).
- Написана функция `NewConfig()`, которая:
  - Регистрирует флаги через `flag.StringVar`.
  - Задаёт значения по умолчанию (`localhost:8080` и `http://localhost:8080`).
  - Парсит аргументы командной строки и возвращает заполненную структуру.
- В `main.go` (функция `run`) конфигурация создаётся при запуске и используется:
  - `cfg.ServerAddress` передаётся в `http.ListenAndServe`.
  - `cfg.BaseURL` передаётся в конструктор хендлера `NewHandler`.
- Обновлена структура `Handler`: добавлено поле `baseURL`, которое используется в `ShortenHandler` при формировании короткой ссылки в ответе.
- Обновлены тесты: в вызовы `NewHandler` добавлен аргумент `baseURL` (используется тестовое значение, например `http://localhost:8080`).

## Зачем
- **Гибкость:** Теперь сервис можно запускать на любом порту и с любым доменом без изменения исходного кода.
- **Стандартизация:** Использование пакета `flag` — это идиоматичный способ работы с аргументами командной строки в Go.
- **Расширяемость:** Появление отдельного пакета `config` позволяет легко добавлять новые настройки (например, строку подключения к БД, уровень логирования) в будущем.

## Проблемы и решения
- **Проблема:** После добавления `baseURL` в `NewHandler` сломались старые тесты (компиляция не проходила из-за неверного количества аргументов).
- **Решение:** Во всех тестах обновлены вызовы `NewHandler(repo, "http://localhost:8080")`. Это не изменило логику тестов, но восстановило их работоспособность.

# Разбор темы аргументы командной строки:
Например:
package main

import (
    "flag"
    "fmt"
)

func main() {
    // указываем имя флага, значение по умолчанию и описание
    imgFile := flag.String("file", "", "input image file")
    // делаем разбор командной строки
    flag.Parse()
    fmt.Println("Image file:", *imgFile)
}

После запуска программы, например, ./main -file=cat.png, то:
1. imgFile := flag.String("file", "", "input image file"):
   этой командой мы объявляем флаг (конкретно "file" - это первый аргугемнт в функции flag.String). И функция flag.String не парсит (т.е. разбор текста (в данном случае из командной строки) на понятные программе части) аргуметы сразу, т.к. программа еще не знает, что ввёл пользователь, за это отвечает flag.Parse().
   flag.String() - эта функция как бы говорит пакету flag: "если в аргументах командной строки встретишь -file, положи его значение в переменную imgFile. И если флага вообще не будет, исользуй пустую строку "" по умолчанию (это второй аргумент в flag.String(), там мы указываем значение по умолчанию).
   И flag.String() возвращает укзатель (*string) на строку. Поэтому imgFile будет хранить указатель (адрес в памяти) и если в дальнейшем использовать imgFile, то нужно разыменовывать (*imgFile) чтобы получить именно значение, в противном случае мы будем получать только адрес.

2. flag.Parse():
   Эта функция уже конктрено занимается парсингом командной строки, т.е. смотрит на то, что реально ввёл пользователь в консоли (в нашем случае -file=cat.png):
- Берет эту строку
- Видит флаг -file
- Находит для него переменную (ту которую декларировали в imgFile := flag.String())
- Записывает туда значение "cat.png"

3. fmt.Println("Image file:", *imgFile):
   И тут мы принтим, разыменовывая указатель, значение которое лежит по адресу *imgFile.
   Если написать просто fmt.Println(imgFile), то вывод будет адрес памяти (0xc000010200)


## Разбор требования инкремента "Флаг -b отвечает за базовый адрес результирующего сокращённого URL (значение: адрес сервера перед коротким URL, например http://localhost:8000/aspdo45gf)"

То есть через флаг (-b) настраиваем, какой домен и порт будет в ответе сервера, когда он возвращает короткую ссылку.

Допустим, запускаем сервер на порту 8080. Флаг -b по умолчанию равен http://localhost:8080.
Клиент присылает длинный URL. Сервер генерирует код, например, aspdo45gf. И теперь сервер должен вернуть полную короткую ссылку. Он берёт значение из флага -b и приклеивает к нему код.
Пример:
- Значение флага -b: http://localhost:8080
- Сгенерированный код: aspdo45gf
- Ответ сервера: http://localhost:8080/aspdo45gf

Для чего это нужно (почему нельзя просто захардкодить):
В случае когда сервер работает не на локальной машине, а на реальном сервере в интернете, то:
- Сам сервер может слушать порт 8080 внутри контейнера (флаг -a: :8080).
- Но снаружи, в интернете, он доступен по красивому адресу https://short.mycompany.com (через Nginx или балансировщик).
Если вы захардкодите http://localhost:8080, то пользователи получат нерабочие ссылки. А если используете флаг -b, вы запускаете сервис так:
./shortener -a :8080 -b https://short.mycompany.com

И сервер будет возвращать: https://short.mycompany.com/aspdo45gf. то правильная и рабочая ссылка.

То есть в коде:
Ранее в ShortenHandler была строка:
fmt.Fprintf(w, "http://localhost:8080/%s", code)
И теперь заменяем захардкоженный http://localhost:8080 на значение из конфига (h.baseURL):
fmt.Fprintf(w, "%s/%s", h.baseURL, code)

## Итого: 
Флаг -b — это «префикс» для коротких ссылок. Он говорит серверу: «Когда будешь возвращать короткий URL, напиши перед кодом вот этот адрес». Это позволяет сервису работать на разных доменах и портах без изменения кода.


# Способы декларации флагов

## Почему flag.StringVar?
В Go есть два способа работы с флагами:
- flag.String("a", "default", "help") — возвращает указатель на строку (*string). С ним неудобно работать напрямую.
- flag.StringVar(&переменная, "a", "default", "help") — сразу записывает значение в переменную. Это чище и удобнее. Рекомендую использовать именно StringVar.
