# Инкремент 12. Массовые операции (batch) и транзакции. Массовое сокращение URL (Batch API) и исправление синхронизации счётчика

По инкременту нужно добавить новый эндпоинт, который принимает массив URL, сохраняет их (в БД, файл или память) и возвращает массив коротких ссылок.

## Что нужно сделать:
1. Новый маршрут: POST /api/shorten/batch.
2. Новые структуры: для запроса (BatchRequest) и ответа (BatchResponse).
3. Новый метод в Repository: SaveBatch(ctx, records []URLRecord) error.
4. Реализация SaveBatch во всех трёх хранилищах (Postgres, File, Memory).
5. Транзакция в Postgres: сохранить весь батч за один запрос (или в одной транзакции), чтобы избежать частичных сохранений.
6. Обработка gzip: ваш middleware уже это делает, так что просто не забывайте, что тело может быть сжато.

## Что сделано
- **Новый эндпоинт `POST /api/shorten/batch`:**
  - Принимает JSON-массив объектов `[{"correlation_id": "...", "original_url": "..."}]`.
  - Возвращает JSON-массив `[{"correlation_id": "...", "short_url": "..."}]`.
  - Отклоняет пустой батч с кодом `400 Bad Request`.
- **Новый метод в интерфейсе `Repository`:**
  - `SaveBatch(ctx context.Context, records []URLRecord) error`.
- **Реализация `SaveBatch`:**
  - **PostgresStorage:** использует транзакцию (`tx.Begin()` / `tx.Commit()`). Это гарантирует, что либо сохранятся все записи, либо ни одной (атомарность).
  - **FileStorage:** последовательно дописывает каждую запись в файл.
  - **MemoryStorage:** сохраняет все записи в карту под защитой мьютекса.
- **Исправление синхронизации счётчика с PostgreSQL:**
  - Ранее `GetMaxUUID` пытался выполнить `CAST(uuid AS INTEGER)`, что вызывало ошибку `SQLSTATE 22P02` при попытке преобразовать Base62-код (например, `"A"`) в число.
  - Добавлена функция `shortener.FromBase62(s string) int64`, которая декодирует Base62-строку обратно в число.
  - Метод `GetMaxUUID` заменён на `GetMaxShortURL`, который получает все `short_url` из БД, декодирует их через `FromBase62` и находит максимальное значение.
  - В `main.go` счётчик `shortener` синхронизируется с этим максимальным значением при старте сервера.

## Зачем
- **Производительность:** Batch API позволяет сокращать множество URL за один запрос, снижая нагрузку на сеть и сервер.
- **Атомарность:** Транзакция в PostgreSQL защищает от частичных сохранений (если одна запись не сохранилась, откатываются все).
- **Корректная нумерация:** Синхронизация счётчика с БД гарантирует, что после перезапуска сервера новые коды не будут конфликтовать с уже существующими.
- **Обратная совместимость:** Существующие эндпоинты (`POST /`, `POST /api/shorten`) продолжают работать.

## Проблемы и решения
- **Проблема:** При запуске сервера возникала ошибка `неверный синтаксис для типа integer: "A"`.
- **Причина:** PostgreSQL не умеет преобразовывать Base62-строки в числа.
- **Решение:** Декодирование Base62 перенесено на сторону Go (функция `FromBase62`). SQL-запрос больше не пытается выполнить `CAST`.
- **Проблема:** Возможна гонка данных при параллельных запросах к памяти или файлу.
- **Решение:** В `MemoryStorage` и `FileStorage` методы `SaveBatch` защищены мьютексом.
